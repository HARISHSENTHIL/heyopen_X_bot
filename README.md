# heyopen_x_bot

Tag the bot under any X post (`@yourbotname explain this`) and it replies with a short
explanation, generated by Claude. v1 scope is "ask only" — no verify/compare/image yet.

## How it works

A background poller hits `GET /2/users/:id/mentions` every `POLL_INTERVAL_SECONDS`,
pulls in the parent/quoted post as context, asks Claude for a short answer, and posts
it as a reply via `POST /2/tweets`. State (last-seen mention, daily reply counts) lives
in a local sqlite file — no external services needed for v1.

## Prerequisites

- **Python 3.10+**
- **X (Twitter) developer app** — [console.x.com](https://console.x.com), Keys & Tokens tab. You need:
  - Consumer Key / Secret and Bearer Token (app-level)
  - **Access Token / Access Token Secret for the bot account itself.** These are
    separate from the app-level keys: enable "OAuth 1.0a" user authentication
    with **Read and Write** permission on the app, then generate the access
    token/secret while logged in as the account that will own the bot handle.
    Without these, the bot can read mentions but can't post replies.
- **Anthropic API key** — [console.anthropic.com](https://console.anthropic.com)

## Running the application

```bash
# 1. Clone the repo
git clone https://github.com/<your-org>/heyopen_x_bot.git
cd heyopen_x_bot

# 2. Create & activate a virtual environment
python -m venv .venv
source .venv/bin/activate        # macOS / Linux
# .venv\Scripts\activate         # Windows

# 3. Install dependencies
pip install -r requirements.txt

# 4. Configure environment variables
cp .env.example .env
# Open .env and fill in all required values (X keys, Anthropic key, etc.)

# 5. Start the server (with auto-reload for development)
uvicorn app.main:app --reload
```

The background mention-poller starts automatically with the server.
Once running, you can hit these endpoints:

| Endpoint       | Description                                      |
|----------------|--------------------------------------------------|
| `GET /health`  | Simple health check — returns `{"status": "ok"}` |
| `GET /status`  | Last poll time and today's reply count            |

By default the server runs on **http://127.0.0.1:8000**. To change the
host/port: `uvicorn app.main:app --host 0.0.0.0 --port 8080`.

## Cost / rate controls

X's API is pay-per-use with a funded balance — every mention read and every reply
costs something, and a viral tag can dump a burst of mentions at once. Two guards are
built in:

- `MAX_REPLIES_PER_DAY` — hard global cap
- `MAX_REPLIES_PER_AUTHOR_PER_DAY` — stops one person from draining the budget

Tune both in `.env` once you have a feel for real traffic and your X API balance.

## US-only gate

`REQUIRE_US_AUTHOR=true` makes the bot reply only to accounts that look US-based.

**Read this before trusting it.** X's API exposes no account-country field. The
"Account based in" value shown in X's *About this account* panel is not available
through API v2 — there is no `user.fields` value for it and no search operator.
The only first-party signal is `location`, a **free-text string the user types into
their own profile**, which X's own docs describe as "a freeform value [that] may not
indicate a valid location."

So `app/geo.py` parses that string. Consequences you are opting into:

- **Spoofable.** Anyone can type "New York" and pass the gate.
- **Rejects real US users.** A blank profile location counts as non-US, and a large
  share of accounts leave it blank. This is the gate's main cost.
- **Resolution is heuristic.** An unambiguous US marker beats a foreign one, so
  "London, Kentucky" and "Paris, TX" pass while bare "London" does not. Two-letter
  state codes are only trusted in trailing `City, ST` position, and codes that
  collide with country codes (`CA`, `IN`, `DE`, `GA`…) are consulted last.

Treat it as a **traffic and cost filter, not an identity control.** `GET /status`
reports `skipped_non_us` and `skipped_unverified` so you can measure what the gates
are actually turning away before deciding whether the tradeoff is worth it.

If you need something stronger, the options are a third-party scraper that exposes
`account_based_in` (against X's terms, adds per-mention cost and latency, and the
underlying value is IP-derived so it breaks on travel and VPNs) or enterprise
Profile Geo (`user.derived.locations.country_code`, enterprise-tier only, and X
documents that only ~30% of accounts resolve to country level). Neither is
authoritative. `is_us_location()` in `app/geo.py` is the single seam to swap if you
go that route.

Note that `verified_type` only means the account pays for X Premium. If the goal is
abuse control rather than geography, `is_identity_verified`, account age
(`created_at`) and a `public_metrics.followers_count` floor are free, unspoofable
signals worth more than a location gate.

## Policy notes (worth re-checking before scaling up)

- X's automation rules treat AI-powered reply bots as a distinct category; this bot is
  built to only reply when explicitly @mentioned (one reply per interaction, user-initiated),
  which is the compliant shape described in X's rules — but verify current policy on
  X's developer site before high-volume launch, since this area has shifted more than
  once in 2026.
- Post/parent text is passed to Claude as data, never as instructions (see
  `app/llm.py` system prompt) — a tagged post can't hijack the bot's behavior by
  embedding fake instructions in its text.

## Swapping the model

`ANTHROPIC_MODEL` in `.env` controls which Claude model answers. `app/llm.py` is the
only file that talks to Anthropic — swap providers there if needed later.
